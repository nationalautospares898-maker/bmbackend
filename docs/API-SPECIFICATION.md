# API Specification — `bmbackend`

| Field | Value |
|---|---|
| Status | **Phase 1 proposal — no endpoint is implemented** |
| Base path | `/api/v1` |
| Transport | HTTPS only |
| Content type | `application/json` (`multipart/form-data` for uploads) |
| Case convention | `snake_case` in all JSON bodies and query parameters |

> This document is the **contract the backend owns**. The frontend's view of the same contract is

> here. Where the two disagree, this document wins and the frontend document is corrected.

## 1. Conventions

### 1.1 Why `snake_case`

Postgres, SQLAlchemy and Pydantic are all `snake_case`. Converting at the API boundary would add a
mapping layer on both sides whose only product is a new class of bug (field renamed on one side
only). The frontend generates TypeScript types from the OpenAPI document, so it never hand-writes
field names. See ADR-012.

### 1.2 Standard headers

| Header | Direction | Purpose |
|---|---|---|
| `Authorization: Bearer <access_token>` | → | Required on everything except `/auth/login`, `/auth/refresh`, `/healthz`, `/readyz` |
| `X-Request-Id` | ↔ | Client-supplied correlation id (UUID); generated if absent, always echoed |
| `X-Device-Id` | → | Registered device UUID; required on all authenticated calls |
| `X-Counter-Id` | → | Required on billing, draft, sale, payment endpoints |
| `Idempotency-Key` | → | **Required** on every mutating financial endpoint (§5) |
| `If-Match` | → | Draft `version` for optimistic concurrency on draft updates |
| `Idempotent-Replay: true` | ← | Present when a stored response was returned instead of new work |
| `X-Api-Version` | ← | Server build/API version, for client compatibility warnings |

### 1.3 Scoping

`business_id` and `branch_id` are **never accepted from the client** as a way to select a tenant.
They are derived from the authenticated token and the active membership. Sending them is ignored,
except where an owner explicitly switches branch via `POST /auth/select-branch`, which re-issues the
access token with the new scope.

### 1.4 Pagination

List endpoints are cursor-paginated:

```
GET /api/v1/products?query=brake&limit=20&cursor=eyJrIjoi...
```
```json
{
  "items": [ ... ],
  "page": { "next_cursor": "eyJrIjoi...", "has_more": true, "limit": 20 }
}
```
`limit` default 20, **hard maximum 50** for search and 200 for plain lists (NFR-PERF-006). Report
endpoints use `page`/`page_size` with a documented max and return `total_count`.

### 1.5 Timestamps, money, quantities

- Timestamps: RFC 3339 with offset, e.g. `2026-10-29T11:04:08+05:30`. Server time is authoritative.
- Money and quantities: **JSON strings**, never numbers — `"1234.50"`, `"2.000"`. This prevents
  IEEE-754 corruption in JavaScript. The frontend parses them with a decimal library for display
  and arithmetic previews. See ADR-013.
- Percentages: strings, e.g. `"18.000"`.

## 2. Authentication

### `POST /api/v1/auth/login`
```json
{ "username": "ravi", "password": "…", "device": { "id": "<uuid>", "label": "Counter 1 PC" } }
```
→ `200`
```json
{
  "access_token": "…", "token_type": "bearer", "expires_in": 900,
  "user": { "id": "…", "full_name": "Ravi", "must_change_password": false },
  "business": { "id": "…", "display_name": "NATIONAL AUTO SPARES" },
  "branches": [ { "id": "…", "code": "MAIN", "name": "Main Shop" } ],
  "active_branch_id": "…",
  "role": "cashier",
  "permissions": ["billing.draft.manage", "billing.sale.finalize", "..."],
  "server_time": "2026-10-29T11:04:08+05:30"
}
```
The refresh token is set as an `HttpOnly; Secure; SameSite=Lax; Path=/api/v1/auth` cookie and is
**never** in the body (NFR-SEC-003).

Errors: `401 INVALID_CREDENTIALS`, `423 ACCOUNT_LOCKED` (with `retry_after_seconds`),
`403 USER_INACTIVE`, `403 DEVICE_REVOKED`, `429 RATE_LIMITED`.

### `POST /api/v1/auth/refresh`
No body; uses the cookie. Rotates the refresh token. Reuse of a consumed token →
`401 REFRESH_TOKEN_REUSED` and the whole family is revoked (FR-AUTH-002).

### `POST /api/v1/auth/logout`
Revokes the current refresh family and clears the cookie.

### `POST /api/v1/auth/pin-switch` *(P1, FR-AUTH-005)*
`{ "username": "sunil", "pin": "1234" }` on an already-trusted device → new access token for that
user. Rate-limited to 5 attempts, then a full password login is required.

### `GET /api/v1/auth/me`
Returns the current context: user, business, active branch, counter, role, permissions, server time,
and `tax_mode` so the client knows whether to render `ESTIMATE` or `TAX INVOICE`.

### `POST /api/v1/auth/select-branch`
`{ "branch_id": "…" }` → new access token scoped to that branch. Rejected if the membership does
not cover it.

### 3.3 Sale finalisation — the critical endpoint

### `POST /api/v1/sales:finalize`
Permission `billing.sale.finalize`. **`Idempotency-Key` required.**

```json
{
  "draft_id": "<uuid>",
  "draft_version": 7,
  "counter_id": "…",
  "sale_type": "cash",
  "customer": {
    "mode": "existing",
    "customer_id": "…"
  },
  "header": {
    "customer_name": "Imran", "customer_business_name": "Imran Transport",
    "vehicle_number": "KA 01 AB 1234", "mechanic_name": "Suresh",
    "phone": "98xxxxxxxx", "notes": null, "due_date": "2026-11-28"
  },
  "lines": [
    { "product_id": "…", "quantity": "2.000", "unit_price": "1250.0000",
      "price_source": "catalog", "discount_percent": "0.000" }
  ],
  "invoice_discount": { "percent": "0.000", "amount": "0.00" },
  "payment": { "method": "cash", "amount": "2500.00", "reference": null },
  "client_computed_total": "2500.00",
  "accept_price_changes": false,
  "oversell_override": null
}
```

- `sale_type` ∈ `cash` | `credit`. **Same engine, same endpoint, same atomicity for both**
  (C-6, FR-SALE-009, FR-CREDIT-008). A credit sale finalises immediately on this call — there is no
  preparatory step, no second endpoint, and no "pending credit" state.
- `customer.mode` ∈ `none` (cash, free-text name only) | `existing` | `new`. `new` carries a
  **client-generated `customer_id`** so the creation is idempotent and offline-safe (FR-CUST-003).
  For `new`, **only `name` is required** — every other customer field is optional and is persisted
  if supplied (FR-CUST-010, FR-CREDIT-012). `credit` requires `existing` or `new`; a free-text name
  alone is rejected with `409 CREDIT_CUSTOMER_REQUIRED` (FR-CUST-002, FR-CREDIT-009).
- `payment` is **optional for `sale_type: credit`** and is not expected at save time. Omit it and the
  invoice is simply `unpaid`; payment is collected later via `POST /payments` (FR-CREDIT-025).
  For `sale_type: cash` it is required and must cover the total.
- `header` fields (vehicle, mechanic, phone, business name, notes) are **optional for both sale
  types** and are snapshotted onto the invoice when present (FR-CREDIT-012).
- `lines` are sent explicitly rather than read from the draft, so the client's intent is
  unambiguous. `draft_version` must match the server's draft, otherwise `409`.
- `client_computed_total` is a **cross-check only** (FR-SALE-003).
- `oversell_override`: `{ "reason": "Customer waiting, stock miscount, verified physically" }`.

**Response `201`:**
```json
{
  "invoice": {
    "id": "…", "invoice_number": "NAS/2026-27/00412", "sequence_number": 412,
    "document_kind": "estimate",
    "status": "issued", "issued_at": "2026-10-29T11:05:12+05:30",
    "is_credit": false, "due_date": null,
    "customer": { "id": null, "name_snapshot": "Imran", "business_name_snapshot": null,
                  "vehicle_number_snapshot": "KA 01 AB 1234",
                  "mechanic_name_snapshot": "Suresh", "phone_snapshot": "98xxxxxxxx" },
    "items": [
      { "line_no": 1, "product_name_snapshot": "Brake Shoe Set — Tata 407",
        "sku_snapshot": "TT-407-BS", "unit_code_snapshot": "SET",
        "quantity": "2.000", "unit_price": "1250.0000",
        "discount_amount": "0.00", "tax_rate_snapshot": "0.000",
        "tax_amount": "0.00", "line_total": "2500.00" }
    ],
    "subtotal": "2500.00", "discount_total": "0.00", "tax_total": "0.00",
    "rounding_adjustment": "0.00", "total": "2500.00",
    "amount_paid": "2500.00", "outstanding": "0.00", "payment_status": "paid",
    "oversell_override": false,
    "counter": { "id": "…", "code": "C1" },
    "created_by": { "id": "…", "full_name": "Ravi" }
  },
  "print_payload": { "...": "see §3.4" },
  "warnings": [
    { "code": "LOW_STOCK_AFTER_SALE", "message": "Brake Shoe Set — Tata 407 now at 2" }
  ]
}
```

**Error responses — all documented, all client-handled:**

| Status | Code | Body detail | Client action |
|---|---|---|---|
| 409 | `INSUFFICIENT_STOCK` | `lines: [{product_id, name, requested, available}]` | Show shortfall; offer qty fix or (if permitted) override |
| 409 | `PRICE_CHANGED` | `lines: [{product_id, name, draft_price, current_price}]` | Show diff; user accepts or edits (E-5) |
| 409 | `DRAFT_VERSION_CONFLICT` | `current_state` | Reconcile before retry (E-4) |
| 409 | `DRAFT_ALREADY_FINALIZED` | `invoice: {...}` | Show the existing invoice — **do not create another** |
| 409 | `IDEMPOTENCY_KEY_REUSE` | `conflicting_fingerprint` | Client bug; log and alert |
| 409 | `IDEMPOTENT_REQUEST_IN_PROGRESS` | `retry_after_ms` | Retry same key with backoff (E-1/E-2) |
| 409 | `PRODUCT_INACTIVE` | `lines: [...]` | Remove or reactivate (E-15) |
| 422 | `TOTAL_MISMATCH` | `server_total`, `client_total` | Refresh draft; never override silently |
| 422 | `VALIDATION_ERROR` | `fields: {...}` | Field-level messages |
| 403 | `PERMISSION_DENIED` | `required_permission` | Explain, offer supervisor login |
| 403 | `OVERSELL_NOT_PERMITTED` | `required_permission` | Offer supervisor override |
| 422 | `OVERSELL_REASON_REQUIRED` | — | Force a reason ≥ 10 chars |
| 409 | `CREDIT_LIMIT_EXCEEDED` | `limit`, `current_outstanding`, `this_sale` | Warn or block per settings |
| 503 | `SERVICE_UNAVAILABLE` | `retry_after_ms` | Queue in outbox, keep key (E-1) |

### 3.4 Invoices and printing

| Endpoint | Permission | Notes |
|---|---|---|
| `GET /invoices?from=&to=&branch_id=&payment_status=&customer_id=&counter_id=&cursor=` | `reports.sales.read` | Backs Daily Bills and Credit Bills — **one dataset, two views** (FR-RPT-003) |
| `GET /invoices/{id}` | `reports.sales.read` | Full invoice with items |
| `GET /invoices/{id}/print-payload?copy=reprint` | `reports.sales.read` | Everything needed to render the document (FR-PRINT-001) |
| `POST /invoices/{id}:cancel` | `billing.sale.cancel` | `{ "reason": "…" }`, `Idempotency-Key` required (FR-SALE-011) |
| `POST /invoices/{id}/print-events` | `reports.sales.read` | Records a print attempt (FR-PRINT-004); failure to log never blocks printing |

**There is deliberately no `PUT`/`PATCH`/`DELETE` on invoices or invoice items** (FR-SALE-010).

**`print_payload` shape** — the backend decides the content, the frontend decides the pixels:
```json
{
  "document_title": "ESTIMATE",
  "is_duplicate": false,
  "business": {
    "display_name": "NATIONAL AUTO SPARES",
    "address_lines": ["…", "…"], "phone_numbers": ["…"],
    "tax_identifier": null, "tax_identifier_label": null
  },
  "issued_at": "2026-10-29T11:05:12+05:30",
  "customer": { "name": "Imran", "business_name": "Imran Transport",
                "vehicle_number": "KA 01 AB 1234", "mechanic_name": "Suresh",
                "phone": "98xxxxxxxx" },
  "columns": ["sl_no", "item", "quantity", "price", "total"],
  "lines": [ { "sl_no": 1, "item": "Brake Shoe Set — Tata 407",
               "quantity": "2", "price": "1250.00", "total": "2500.00" } ],
  "totals": { "subtotal": "2500.00", "discount": "0.00", "tax": null,
              "rounding": "0.00", "grand_total": "2500.00" },
  "amount_in_words": "Two Thousand Five Hundred Rupees Only",
  "payment": { "status": "paid", "amount_paid": "2500.00", "outstanding": "0.00",
               "method": "cash", "due_date": null },
  "footer_notes": [],
  "tax_mode": "estimate_only"
}
```
`document_title`, `tax_identifier_label` and `totals.tax` are driven by `tax.mode`. While
`estimate_only`, `totals.tax` is `null` (not `"0.00"`) so the frontend renders **no tax row at all**
rather than a misleading zero — and `document_title` can never be `TAX INVOICE` (FR-PRINT-002,
FR-TAX-004).

**The print payload is identical in shape for cash and credit invoices** (FR-CREDIT-030). A credit
invoice differs only in `payment.status`, `payment.outstanding` and `payment.due_date`. The
**document design never varies by sale type** — the client renders one layout
(`../../bmfrontend/docs/UI-UX-SPECIFICATION.md §12`) and the backend never emits a second one.

**Owner-decision consequences for this payload** (2026-10-29):

| Field | Rule |
|---|---|
| ~~`invoice_number`~~ | ❌ **REMOVED from `print_payload`.** [OD-3](OWNER-DECISIONS.md#od-3) is re-answered — *"No need of invoice numbering."* The internal reference stays on the `invoice` resource for audit and reconciliation, but **the print payload must not carry it and the client must not render one**. Revives only under [OD-25](OWNER-DECISIONS.md#od-25). |
| `payment.*` | Carries the **true recorded** `amount_paid`, `outstanding` and `due_date` from invoice and allocation records (FR-CREDIT-002). The client renders them for **credit** bills; it never recomputes them (FR-PRINT-020). |
| `document_title` | **`ESTIMATE`** for cash and credit alike while `tax.mode = estimate_only` ([OD-24](OWNER-DECISIONS.md#od-24)). The server never substitutes `BILL`/`INVOICE`, and cannot emit `TAX INVOICE` until the `FR-TAX-003` gate passes. |
| Amount values | Emitted as **exact decimal strings** (ADR-013). **Display formatting is the client's concern** ([OD-23](OWNER-DECISIONS.md#od-23)) — the server never pre-formats, pads or truncates, and never rounds a value for presentation. |

### 3.7 Credit and payments

| Endpoint | Permission | Notes |
|---|---|---|
| `GET /credit/outstanding?customer_id=&ageing_bucket=&cursor=` | `credit.read` | Derived from authoritative data (FR-CREDIT-002) |
| `GET /credit/ageing-summary?as_of=` | `credit.read` | Buckets: current, 1–30, 31–60, 61–90, 90+ |
| `POST /payments` | `credit.payment.record` | **`Idempotency-Key` required** (FR-PAY-004) |
| `GET /payments?customer_id=&from=&to=&cursor=` | `credit.read` | |
| `POST /payments/{id}:reverse` | `credit.payment.record` | `{reason}`; creates a reversal, never edits (FR-PAY-005) |
| `POST /credit-notes/{id}/allocations` | `credit.payment.record` | Allocate a credit note to invoices |
| `POST /credit/write-off` | `credit.writeoff` | Owner only; produces a credit note with reason |

**`POST /payments` request:**
```json
{
  "customer_id": "…",
  "amount": "5000.00",
  "method": "upi",
  "reference": "UPI/12345",
  "received_at": null,
  "allocation": { "strategy": "oldest_first" },
  "notes": null
}
```
`allocation.strategy` ∈ `oldest_first` | `invoice_specific` (with
`allocations: [{invoice_id, amount}]`) | `manual`. Any remainder becomes on-account customer credit
(FR-PAY-003). Over-allocating an invoice → `422 OVER_ALLOCATION` (FR-PAY-007).

**There is no endpoint, anywhere, that sets `payment_status` or `amount_paid` directly** — they are
derived (FR-CREDIT-003). There is likewise no "mark as paid" endpoint: full payment is reached only
by recording payments whose allocations sum to the invoice total.

**Recording a payment never moves stock.** `POST /payments` writes payment and allocation rows only;
it touches no `stock_movements` row and cannot re-deduct the sale's inventory (FR-CREDIT-010). Sale
finalisation and payment collection are distinct financial events with distinct endpoints.

#### Customer-wise credit listing (FR-CREDIT-011, FR-RPT-028)

| Endpoint | Permission | Notes |
|---|---|---|
| `GET /credit/customers?include_settled=&ageing_bucket=&query=&cursor=` | `credit.read` | **One new endpoint.** Customers with credit history plus server-computed aggregates — the top level of the Credit Bills view |

```json
{
  "items": [
    { "customer": { "id": "…", "name": "ANAS", "primary_phone": "98xxxxxxxx" },
      "invoice_count": 3, "open_invoice_count": 2,
      "total_invoiced": "30,680.00", "total_paid": "7,200.00",
      "outstanding": "23,480.00",
      "oldest_due_date": "2026-10-17", "days_overdue": 12,
      "ageing": { "current": "3480.00", "d1_30": "0.00", "d31_60": "20000.00",
                  "d61_90": "0.00", "d90_plus": "0.00" } }
  ],
  "summary": { "overall_outstanding": "284500.00", "overall_overdue": "46200.00",
               "customers_with_balance": 32 },
  "page": { "next_cursor": "…", "has_more": true, "limit": 20 },
  "as_of": "2026-10-29T11:04:08+05:30"
}
```

The **second level reuses the existing invoice endpoint** — no new contract was added for it:
`GET /invoices?customer_id=<id>&is_credit=true&cursor=` returns that customer's individual invoices,
each already carrying `invoice_number`, `issued_at`, `total`, `amount_paid`, `outstanding`,
`payment_status` and `due_date`.

Payment history per invoice likewise reuses `GET /payments?invoice_id=<id>`.

Rules:
- `include_settled` defaults to `false` (outstanding view). `true` includes customers at zero — their
  invoice history is never deleted or permanently hidden (FR-RPT-031).
- All aggregates are **server-computed** from invoice totals and valid allocations. The client never
  sums them as authoritative (FR-RPT-030, ADR-032).
- Grouping is keyed on `customer_id`. A renamed customer changes only the `name` label here
  (FR-RPT-029, FR-CUST-011).
- **No per-customer table, folder or directory exists** — this endpoint is an aggregate query over
  `invoices` and `payment_allocations` (`DATA-MODEL.md §3.9`).

### 3.12 Synchronisation

### `POST /api/v1/sync/operations`
```json
{
  "device_id": "…",
  "operations": [
    { "op_id": "<uuid>", "client_seq": 1041, "type": "draft.upsert",
      "entity_type": "draft_bill", "entity_id": "<draft uuid>",
      "base_version": 3, "client_created_at": "…", "payload": { "...": "as PUT /drafts/{id}" } },
    { "op_id": "<uuid>", "client_seq": 1042, "type": "customer.upsert",
      "entity_type": "customer", "entity_id": "<customer uuid>",
      "base_version": null, "client_created_at": "…", "payload": { "...": "" } }
  ]
}
```
→ `200` (always 200 if the batch itself was well-formed; per-operation outcomes are in the body)
```json
{
  "results": [
    { "op_id": "…", "status": "accepted", "server_state": { "...": "draft" } },
    { "op_id": "…", "status": "conflicted",
      "error": { "code": "DRAFT_VERSION_CONFLICT", "message": "…" },
      "server_state": { "...": "current draft" } }
  ],
  "server_time": "…"
}
```
`status` ∈ `accepted` | `replayed` | `conflicted` | `rejected` (FR-OFFLINE-005). Batch max 100
operations; ordering is preserved per `entity_id`, and the first failure for an entity skips that
entity's remaining operations while others proceed.

### `GET /api/v1/sync/catalog?since=<cursor>&limit=`
Returns a bounded delta of products, prices, aliases and branch stock for the client cache, plus
`next_cursor`, `has_more`, and `reset_required: true` when the cursor is too old to serve
(FR-OFFLINE-008). Row cap from `settings.sync.catalog_cache_max_rows`.

### `GET /api/v1/sync/bootstrap`
One call after login: active branch, counter, permissions, settings relevant to the client
(`max_open_drafts`, `tax.mode`, rounding, discount caps), server time, and the catalog cursor.

**There is no sync operation type for finalising a sale, recording a payment, confirming a purchase,
creating a return or applying an import.** This is an intentional, enforced boundary
(FR-OFFLINE-002).

## 4. Error envelope

Every non-2xx response, without exception:

```json
{
  "error": {
    "code": "INSUFFICIENT_STOCK",
    "message": "Not enough stock for 1 item.",
    "details": {
      "lines": [ { "product_id": "…", "name": "Brake Shoe Set — Tata 407",
                   "requested": "5.000", "available": "4.000" } ]
    },
    "request_id": "01JBQ…",
    "retryable": false
  }
}
```

| Field | Rule |
|---|---|
| `code` | Stable `SCREAMING_SNAKE_CASE`. **Clients branch on `code`, never on `message`.** Codes are additive-only; removing or renaming one is a breaking change. |
| `message` | Short, human-readable, safe to show. Never contains SQL, stack traces, file paths or internal ids. |
| `details` | Machine-readable specifics, shape documented per code. |
| `request_id` | Always present, matches the log line and `X-Request-Id`. |
| `retryable` | Whether an identical retry could succeed (drives the client's outbox). |

### 4.1 Status code usage

| Status | Used for |
|---|---|
| 400 | Malformed request (bad JSON, bad header) |
| 401 | Missing/invalid/expired access token |
| 403 | Authenticated but not permitted, or device revoked, or wrong branch scope |
| 404 | Resource absent **within the caller's tenant** — a cross-tenant id returns 404, never 403, so existence is not leaked |
| 409 | Business-rule conflict (stock, price, version, idempotency, state) |
| 413 | Upload too large |
| 415 | Unsupported upload type |
| 422 | Schema-valid but semantically invalid |
| 423 | Account locked |
| 428 | Required precondition missing — `If-Match` absent on an existing draft (`PRECONDITION_REQUIRED`, §6) |
| 429 | Rate limited, with `Retry-After` |
| 500 | Unexpected — generic `INTERNAL_ERROR` + `request_id` only |
| 503 | Dependency unavailable / shutting down, with `retry_after_ms` |

#### 4.2a Codes added in Phase 2 closure (audit finding CF-3)

The four codes below were **already required by normative text** in this document and in
`OFFLINE-SYNCHRONIZATION.md`, but were missing from this registry while it declared itself "complete
for v1". Because the frontend's `ErrorCode` union is **generated** from this registry and must be
handled in an exhaustive `switch` (ADR-029, `../../bmfrontend/docs/TESTING-STRATEGY.md §8` rule 6),
compliant client code could **never** handle them — an unhandled runtime branch in the offline path.
Codes are additive-only, so this is a **non-breaking** change (§8).

| Code | Status | Emitted by | Semantics | Client behaviour |
|---|---|---|---|---|
| `PRECONDITION_REQUIRED` | **428** | `PUT /drafts/{id}` | `If-Match` was absent on an **existing** draft. The server will not take a blind write to a draft someone else may be editing (§6) | **Client bug.** Report to error tracking, refetch the draft, do not retry blindly |
| `SKIPPED_AFTER_EARLIER_FAILURE` | per-operation, in a `200` sync batch | `POST /sync/operations` | An earlier operation **for the same `entity_id`** was not `accepted`, so this entity's remaining operations were skipped to preserve intra-entity ordering (§3.12, `OFFLINE-SYNCHRONIZATION.md §4.3`) | Keep the operation queued; retry **after** the user resolves the earlier conflict. **Not** an error for other entities |
| `CORRUPT_VERSION` | per-operation, in a `200` sync batch | `POST /sync/operations` | The client's `base_version` is **greater** than the server's — impossible under normal operation (`OFFLINE-SYNCHRONIZATION.md §5.2`). Returned as `rejected` and logged server-side | Surface in the sync panel as needing attention; report to error tracking. **Never** auto-retry |
| `DRAFT_ALREADY_CANCELLED` | per-operation `rejected`, or **409** on a direct call | `POST /sync/operations`, `PUT /drafts/{id}` | A local edit arrived for a draft already cancelled server-side (`OFFLINE-SYNCHRONIZATION.md §5.4`) | Offer **"recreate as a new bill"** with a fresh id so the typed lines are not lost |

**Status-code note.** `SKIPPED_AFTER_EARLIER_FAILURE` and `CORRUPT_VERSION` are **per-operation
outcomes inside a `200` batch response**, not HTTP statuses — the batch endpoint returns `200`
whenever the batch itself was well-formed (§3.12). They still belong in this registry because the
client branches on `code` identically for batch outcomes and HTTP errors.

### 4.3 Warning code registry

Warnings ride along with a **successful** response (`warnings: [{code, message, details}]`). They are
not errors: the operation committed. Clients render them informatively and must **never** treat one
as a failure or a reason to retry.

| Code | Emitted by | Meaning |
|---|---|---|
| `LOW_STOCK_AFTER_SALE` | `POST /sales:finalize` | One or more products fell to or below `reorder_level`; `details.products` lists each with its new quantity |
| `CREDIT_LIMIT_APPROACHED` | `POST /sales:finalize` (credit) | Customer outstanding is within 10% of `credit_limit`, while `credit.enforce_limit` is off |
| `CUSTOMER_DUPLICATE_SUSPECTED` | `PUT /customers/{id}` | A likely duplicate exists; `details.candidates` lists them. **Nothing is merged** |
| `CATALOG_CACHE_TRUNCATED` | `GET /sync/catalog` | The delta hit `cache_policy.max_rows`; offline search will be incomplete |

**Asymmetry by design:** error codes are handled **exhaustively** by the client (an unhandled code is
a compile error), while warning codes are handled **permissively** (an unknown warning renders from
its `message` and is logged). A new warning must never break a completed sale, so warnings are
additive and safe to ignore; errors are not.

## 5. Idempotency contract

| Endpoint | `Idempotency-Key` |
|---|---|
| `POST /sales:finalize` | **Required** |
| `POST /payments`, `POST /payments/{id}:reverse` | **Required** |
| `POST /returns` | **Required** |
| `POST /purchases/{id}:confirm` | **Required** |
| `POST /inventory/adjustments` | **Required** |
| `POST /invoices/{id}:cancel` | **Required** |
| `POST /imports/{id}:apply` | **Required** |
| `POST /sync/operations` | Per-operation `op_id` serves the same role |
| `PUT /drafts/{id}`, `PUT /customers/{id}` | Not needed — the client-generated id makes them naturally idempotent |
| All `GET` | N/A |

A required key that is missing → `422 VALIDATION_ERROR` with `fields: {"Idempotency-Key":
"required"}`. Keys must be UUIDs, are scoped per business and endpoint, and are retained 7 days.
Full semantics in `ARCHITECTURE.md §5.3`.

**The client must reuse the same key for every retry of the same user intent, and generate a new key
for a genuinely new attempt** (e.g. after the user edits the bill). This rule is restated in the
frontend document because it is the single most important thing a client can get wrong.

## 6. Optimistic concurrency

Only `draft_bills` uses it, via `version` (integer, incremented server-side):

```
PUT /api/v1/drafts/{id}
If-Match: 3
```
- Match → applied, response carries `version: 4`.
- Mismatch → `409 DRAFT_VERSION_CONFLICT` with `details.current_state` and
  `details.current_version`.
- Absent `If-Match` on an existing draft → `428 PRECONDITION_REQUIRED`. The server will not take a
  blind write to a draft that someone else may be editing.

Invoices, payments and movements need no concurrency token — they are immutable.

## 8. Versioning and compatibility

- Path-versioned (`/api/v1`). A breaking change means `/api/v2`, with both served during migration.
- **Non-breaking** (ship any time): new endpoint, new optional field, new enum value in a *response*
  the client treats defensively, new error code, new optional header.
- **Breaking** (needs a new version): removing/renaming a field, tightening validation, changing a
  type or unit, changing an error code's meaning, making an optional field required.
- The frontend pins a minimum API version; `GET /api/v1/meta` lets it warn the user when a counter
  is running a stale cached client after a deploy.

## 9. Not provided by this API (deliberately)

- No endpoint mutates a finalised invoice, invoice item, payment, stock movement or audit row.
- No endpoint sets `payment_status`, `amount_paid`, or `inventory_balances.quantity` directly.
- No endpoint accepts a client-computed total as authoritative.
- No endpoint finalises a sale, records a payment, or receives stock while the client is offline.
- No endpoint returns cost prices or margins without `catalog.cost.read`.
- No endpoint accepts `business_id` as a tenant selector.
